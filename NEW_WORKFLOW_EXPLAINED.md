# The new way of working: explained simply

> **Our laptops are for writing code. Colab is for cooking the heavy stuff. Google Drive is the shared fridge where only finished ingredients live. GitHub is the recipe book, so anyone, anywhere, can cook the exact same dish.**

This page merges the one-page summary and the technical guide. Where they disagreed, I picked the safer option and explained why (see the last section).

---

## The 3 golden rules

1. **Code lives in Git, edited in VS Code only.** Colab never holds the master copy of any code.
2. **Big files live on Google Drive, never in Git.** That means data, checkpoints and MLflow runs. Git only keeps a tiny `manifest.json` with fingerprints (sha256).
3. **Colab is a disposable machine.** It downloads the code, reads Drive, writes results back, then is forgotten. Any run can be rebuilt from: **Git commit + data version + config + seed**.

---

## Step by step, the new way

### 1. You write and test code on your laptop, with tiny fake data
Your laptop is the **bathroom-sized kitchen**: fine for chopping one onion, not for cooking for 100 people. So on the laptop you only edit code in VS Code and run tests on **toy data** (200 fake sequences, generated by `make toy`). This takes seconds, and your PC never sounds like a helicopter. 🚁

### 2. You get the real OAS data onto Colab, without torturing your laptop
You need the same 6 big files (about 8GB). Colab's local disk (`/content`) is large (check with `!df -h /content`, it is usually 80+ GB), bigger than your 15GB Drive. It is like **renting a professional kitchen by the hour**.

The best way: **download directly inside Colab** with the `wget` lines that OAS gives you on its download page. This is better than uploading from your PC, because:
- uploading 8GB through the browser is slow and breaks easily;
- a download script is **written down**, so anyone can repeat it.

Right after downloading, save two things: the **links** and the **sha256 of each raw file**. This is your recipe's shopping list.

### 3. You decompress on Colab
`gunzip` on Colab's fast disk takes minutes instead of a slow, noisy hour on your laptop.

### 4. You run the cleaning on Colab, but the code is NOT in the notebook
The notebook is only a **remote control** with 3 cells:
- `BRANCH`: which version of the code to use;
- `CONFIG`: which settings file to use;
- `Run`: go.

The real code is `src/clean_data.py` in GitHub, tested and versioned. The notebook just says: *"Hey Colab, download the latest code from GitHub and run it."* So when your friend runs it, they get the exact same code: no "works on my machine."

What the cleaning does, in order:
1. remove the `-` gaps (OAS aligned sequences contain them);
2. make everything uppercase;
3. keep only sequences made of the 20 amino acids (`^[ACDEFGHIKLMNPQRSTVWY]+$`);
4. **count what you threw away and why** (this goes in the report);
5. remove exact duplicates.

### 5. You cluster with MMseqs2 instead of slow cd-hit
Clustering = grouping almost-identical sequences together. cd-hit does it slowly; **MMseqs2 does the same kind of job much faster**.

```bash
mmseqs easy-cluster vhh_unique.fasta out tmp --min-seq-id 0.9 -c 0.8
```

Two honest notes:
- **Time:** people often say "about 20 minutes". Measure it on your own data and write the real number down. Free Colab has few CPU cores.
- **MMseqs2 is not exactly cd-hit.** The professor's plan says `cd-hit -c 0.9`. Tell him you use MMseqs2, and write the exact command in the report.

Then **split by cluster**, not randomly: whole clusters go to train, or val, or test. Otherwise a near-copy of a training sequence sits in the test set, and your model looks smarter than it is. This is called **data leakage**.

### 6. You save only the outputs to the shared Drive, and you keep the fish bones safe 🐟
The outputs are small (10–50× smaller than raw):
`vhh_unique.txt`, `clusters_vhh.tsv`, `splits/train|val|test_vhh.txt`.

Now the raw 8GB. The one-pager says "delete it." The better advice:

> **Don't throw away the fish bones until you've put the recipe in the freezer.**

Before deleting the raw files from Drive, make sure you can get them back: you saved the **download links + sha256** (step 2), and ideally you keep **one compressed copy** somewhere (an external disk or a personal account). Then yes, free your Drive.

### 7. You write `manifest.json`, the fingerprints
A tiny file with the sha256 of every output file. A copy goes to GitHub in `data_manifest/`. Now anyone can check: **"Is my data exactly the same as yours?"**, because `verify_data.py` answers in one command.

Then:
- tag it `data-v1`;
- copy the data to `releases/data-v1/` on Drive and **never edit it again**. A change = a new version (`data-v2`), the old one stays frozen.

### 8. Team B trains the models on Colab
The same remote-control notebook, now with `CONFIG = configs/vhh_small.yaml`.
- First thing it runs: `verify_data.py`. **If the data changed, it refuses to start.** It is a smoke alarm. 🔔
- Checkpoints (`best.pt`, `last.pt`) are saved straight to Drive.
- Colab sessions die sometimes. The training saves `last.pt` every epoch, so you restart with `RESUME = True` and lose minutes, not hours.
- Every run logs: Git commit, data version, config, seed, and the torch/Python versions.

### 9. You push to GitHub: only code, configs and small results
- One task = one branch = one Pull Request (PR).
- A member of the **other team** reviews it.
- CI runs the tests automatically. **Red = it cannot merge.**
- Small files (figures, CSV tables, a 1,000-sequence FASTA ~130 KB) go in Git. Rule: *under 1 MB and human-meaningful = Git, otherwise Drive.*

The repo stays light, cloning takes seconds. ✅

### 10. A month later, someone asks: "How did you get that result?"
You answer in one line:

> Git commit `a3f91c2`, data version `data-v1`, config `vhh_small.yaml`, seed `42`.

Anyone can rebuild that result. That's the magic. ✨
(It works because the **versions of torch and Python are logged too**. Colab updates itself over time, so "same Linux" is not a promise, but "logged versions" is.)

## Old way vs new way

| Situation | Old way | New way |
|---|---|---|
| Running heavy code | Laptop, hours, crashes | Colab, minutes to ~1 hour (measure it) |
| Windows problems | WSL pain, machine-specific | Colab, a Linux that is easy to restart |
| Sharing code | "Works on my machine!" | `git clone` = same code |
| The 8GB raw data | Stuck on disk or forced into Git | Temporary on Colab; links + sha256 saved; one archived copy |
| Storage cost | Your disk suffers | Free: 15GB Drive fits the outputs |
| "Which data was used?" | No idea | `data-v1` tag + `manifest.json` |
| "Which model, which run?" | No idea | MLflow run + Git commit + config + seed |
| New teammate joins | 1 day of setup pain | About 30 minutes with the Day-0 checklist |

## Where does each thing live?

| Thing | Where | In Git? |
|---|---|---|
| Code (`src/`, `scripts/`, `tests/`), configs, Makefile | GitHub repo | yes |
| Notebooks (outputs stripped) | `notebooks/` | yes |
| Manifest copy | `data_manifest/` | yes (tiny) |
| Small results (figures, CSV, JSON, small FASTA) | `results/` | yes |
| Raw OAS / UniProt | Colab disk during work, then archived | no |
| Clean data + splits | Drive `data/` (Team A writes) | no (sha256 in manifest) |
| Checkpoints | Drive `checkpoints/` (Team B writes) | no |
| MLflow runs | Drive `mlruns/` | no |
| Frozen releases | Drive `releases/` + Git tag | tag only |
| Passwords and tokens | Colab Secrets / local `.env` | **never** |

## The 5 rules to memorize

1. **Never run heavy code on your laptop.** Use Colab.
2. **Never store big files in GitHub.** Drive, processed and small only.
3. **Never write real logic in a notebook.** Put it in `src/` (VS Code); the notebook only calls it.
4. **Never edit data in place.** New version = new name (`data-v2`); the old one stays frozen.
5. **Colab never commits code.** Fix in VS Code, push, then pull again in Colab.

(One extra: **never paste a token anywhere.** If it leaks, revoke it on GitHub right away.)

## What this workflow does NOT solve

- **Colab sessions end and GPU quotas are per account.** Save often; use `RESUME`.
- **Drive has 15GB.** Checkpoints are small now, but watch the quota.
- **MLflow on a synced Drive folder is fragile** with many people at once. Export `results/runs.csv` to Git every Friday as a backup.
- **Branch protection** may be unavailable on a free private GitHub repo. If so, agree as a team: *nobody pushes to `main`.*
- **Scope:** the professor's documents say VHH or peptides. "SH2" appears only in the team's own plan. Confirm with him before spending time on it.
- **The setup is not the goal.** The deliverables are the report, the 6 notebooks and the 10,000 generated sequences.
